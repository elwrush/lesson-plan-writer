# Plan: Upgrade Pedagogical Annotations — DESIGN MECHANISM + Design Blueprint

## Problem

The current three-annotation system names the cognitive principle but never explains **how** the slide design achieves it. Annotations like:

```
<!-- COGNITIVE PRINCIPLE: Consolidation — reviewing learning objectives
     strengthens retention and metacognitive awareness. -->
```

say WHAT (consolidation) and WHY (retention) but never HOW. The agent reading this annotation cannot determine what specific design choices make consolidation manifest on this particular slide — it could apply to any summary slide ever written.

This creates slides that pass the checker but lack intentionality in their fine-grained design.

## Solution

**Two changes:**

1. **Add a fourth mandatory annotation — `DESIGN MECHANISM`** — that bridges principle to implementation by naming the specific visual/interactive/structural choice that operationalizes the principle on this slide.

2. **Add a Design Blueprint phase** before any HTML is written. The agent creates a planning document that enumerates every slide, its pedagogical purpose, and the mechanism for achieving it — all referencing existing templates and the codebase. Only after the blueprint is complete does HTML writing begin.

---

## Part A: The DESIGN MECHANISM Annotation

### Format

```html
<!-- PEDAGOGICAL INTENT: [what the student must SEE happen] -->
<!-- WHY THIS FEATURE: [reveal.js feature + why alternatives fail] -->
<!-- COGNITIVE PRINCIPLE: [name from Mayer's 12, or explain why none applies] -->
<!-- DESIGN MECHANISM: [specific design choices that make the principle manifest — see rubric below] -->
```

### What counts as a mechanism

A mechanism must be a **specific design decision** that would be absent if the principle were ignored. Generic statements ("the teacher clicks to advance") are not mechanisms. A mechanism answers one of:

| Question | Example mechanism |
|----------|------------------|
| What element is visually different from its neighbors, and how? | "The coordinator `and` is bold yellow (#ffdd00) on an otherwise white example sentence — the eye is drawn to it." |
| What prevents cognitive overload? (count, pacing, chunk boundary) | "3 items max per slide. Each row reveals on a separate `data-fragment-index` — the teacher cannot advance past the slide until all 3 are seen sequentially." |
| What earlier content is mirrored verbatim as a retrieval cue? | "Summary restates the objective slide's exact numbered 'I can...' wording — this creates a transfer-appropriate processing cue." |
| What would be different if the principle were violated? (negative test) | "If this slide used fragments instead of static display, each objective would appear one at a time, preventing the student from seeing the full lesson map." |
| How does the student experience this moment-by-moment? | "Student first sees the error sentence at full size (1.2em). On auto-animate advance, the error dims (0.55 opacity) and a corrected version appears below in blue — the simultaneous visibility lets the student compare directly." |

### Mechanism Rubric by Cognitive Principle

For the most common principles, the mechanism must answer the question in the right column:

| Principle | Mechanism MUST specify |
|-----------|----------------------|
| **Signaling** | Which words/elements have visual treatment (color/border/underline)? Why those and not others? |
| **Segmenting** | What is the chunk boundary? Max item count per slide? Click pacing? Why this chunk size? |
| **Temporal Contiguity** | Which elements appear on the SAME click? Why must they be paired? What breaks if they appear separately? |
| **Spatial Contiguity** | What elements are visually adjacent? Why is adjacency critical? What split-attention problem is avoided? |
| **Consolidation** | What earlier slide does this mirror verbatim? What retrieval cue (exact wording/structure) is repeated? Is there an active recall moment? |
| **Worked Example** | Which specific item is modeled? What is the step chain? How does this demo connect to the freer practice that follows? |
| **Pretraining** | What prior knowledge is activated? How does this slide set up the next one? |
| **Coherence** | What has been intentionally stripped out? What extraneous element is absent that might naively be included? |

### Litmus Test

If you can remove the DESIGN MECHANISM annotation and still build the same slide, the mechanism is too vague. A good mechanism describes a design choice **unique to this slide**.

### Concrete examples

**Summary slide (Consolidation):**
```
DESIGN MECHANISM: The summary mirrors the objective slide verbatim —
same numbered structure, same "I can..." phrasing. The only difference
is blue ✓ symbols replacing yellow numbers. This creates a retrieval
cue (transfer-appropriate processing). The teacher elicits each point
("Number 1 — can you do this now?") — the non-animated, non-fragmented
layout forces a pause for active recall, which is the actual mechanism
of consolidation.
```

**Diagnostic entry (Pretraining / same principle applied differently):**
```
DESIGN MECHANISM: The slide uses a 180s timer (not the full 360s from
the lesson plan) because each entry slide has only 3 items. The period
between the two sentences is wrapped in a transparent-border span that
reserves layout space — this ensures the comma+coordinator morph on the
reveal slide has no layout shift. Without this reserved space, the
morph would cause the line to jump, breaking the temporal contiguity.
```

**Formula reveal (Temporal Contiguity):**
```
DESIGN MECHANISM: The simple sentence AND the compound sentence are
both visible on the reveal slide — the simple version dimmed (0.5
opacity), the compound version bright (ffdd00). The new S+V elements
in the compound sentence gain blue borders on reveal. The student is
looking at BOTH versions simultaneously and the border points to what
changed. If the simple version were hidden, the comparison would be
lost — the student would see the compound sentence in isolation, which
is just a sentence, not a lesson.
```

## Part B: Design Blueprint Phase

### Where it fits in the workflow

The Design Blueprint is a NEW phase inserted **after** the lesson plan review and **before** any HTML writing. Currently the flow is:

```
Parse lesson plan → Write annotations → Write HTML
```

The new flow becomes:

```
Parse lesson plan → Design Blueprint → Write annotations → Write HTML
```

### What the Design Blueprint contains

The blueprint is a **planning document** (Markdown, written to the session plans directory) with these sections:

```
1. STAGE-TO-SLIDE MAPPING
   - Enumerate every lesson_plan.stages[] entry
   - Map each to the slide type(s) it produces
   - Identify which template patterns to copy

2. PER-SLIDE DESIGN PLAN (one row per slide)
   | Slide ID | Pedagogical Intent | Feature | Mechanism | Template Ref |
   
3. AUTO-ANIMATE PAIRS CHECK
   - List every auto-animate-id with its slide count
   - Verify: matching IDs, same background, previous slide NOT auto-animate

4. ANSWER SLIDE SIZING
   - Per exercise: item count → slide count → slide IDs
   - Flag any slide with >3 items

5. FRAGMENT VERIFICATION
   - List every fragment slide and its fragment indices
   - Verify: no fragments on objectives, transitions, summaries

6. COLOR & FONT AUDIT
   - Verify all backgrounds match the correct type
   - Verify no font-size below minimums
```

### How the Blueprint is used

The agent creates the blueprint AFTER reading the lesson plan JSON and BEFORE opening any template. The blueprint references template patterns by their type names (e.g., "Type 4: Lead-in Error Auto-animate Pair from reference-slideshow.html") rather than rewriting the HTML patterns.

The blueprint validates the design BEFORE code is written. If the mechanism descriptions are vague or the auto-animate pairs don't check out, the agent catches the problem at the planning stage rather than after writing 887 lines of HTML.

The blueprint is written as a Markdown file and reviewed by the user optionally before HTML generation begins.

## Research Synthesis

From Tavily research on skill design best practices:

1. **Progressive disclosure is the pattern.** Microsoft, Anthropic, SwirlAI, MindStudio, and mgechev/skills-best-practices all converge on the same three-tier loading system:
   - **Tier 1**: Name + description (~100 tokens) — loaded at session start
   - **Tier 2**: Full SKILL.md (<500 lines recommended) — loaded when skill is triggered
   - **Tier 3**: Supplementary files in `references/` — loaded on demand

2. **SKILL.md is the "brain."** It should contain high-level procedural logic, not exhaustive reference tables. Details live in `references/` subdirectory files that the agent reads only when needed.

3. **Extended TOC pattern** (Addy Osmani): Keep a 1-2 line summary per offloaded section inline as an index. The agent sees the TOC at Tier 2 and fetches the full details from Tier 3 when needed. This gives the agent a map without loading all the detail.

4. **"One Task Focus" and "Relevant info only"** (Addy Osmani): "A well-fed AI is like a well-fed function: give it only the inputs it needs for the job at hand." Overlong contexts decrease quality.

5. **"Context length is not a substitute for context quality"** — the goal is not to minimize line count but to ensure every line in the context is directly relevant to the current task.

Splitting procedural steps into reference files would mean the agent has to read a reference file, then come back to SKILL.md, then read another reference file, then come back. This is the "naive context churn" that progressive disclosure is designed to AVOID — the pattern loads reference material on demand but keeps the execution sequence inline.

The goal is not 500 lines at any cost. The goal is that every line in the 695 SKILL.md is there BECAUSE the agent needs it during the build, not just as reference material that could have been fetched on demand.

## Decision: Do NOT Trim Further

The remaining 695 lines are 85% procedural workflow (Steps 0-6) and 15% quick-reference material that the agent needs inline during code generation (fragment class names, annotation format, template reference list). Moving any of these to reference files would force additional Tier-3 reads during the execution path, creating "naive context churn" — the exact pattern progressive disclosure is designed to avoid.

**695 lines for a skill of this complexity is reasonable.** The Microsoft <500-line guideline is a recommendation for typical skills. A build pipeline skill that coordinates template copying, slide generation, CSS stitching, verification, and deployment is inherently dense. The goal is context QUALITY, not a line-count contest.
