# M2 L1 Slideshow Retrospective: Non-Pedagogical → Good

## What changed — a catalogue of fixes

### 1. Title slide (r-stack letterbox → full-screen background)
- **Before**: `r-stack` wrapper with positioned `<img>` — content compressed into letterbox, logo 78px, h2 at default ~1.6em, subheader 0.7em
- **After**: `data-background-image` + `data-background-color` + `style="justify-content: center;"` — full-screen image, logo 120px, h2 2.2em, subheader 1em, opacity 0.85
- **Principle violated**: Signal via image, but content was invisible

### 2. Lead-in errors (static → auto-animate pairs)
- **Before**: Single slide with static before/after text — errors visible immediately, no clickthrough
- **After**: 2 auto-animate pairs (entry→reveal per error). Entry shows error with transparent borders on problem words. Reveal dims original, shows correction with blue underlines
- **Principle violated**: Temporal contiguity — error + correction must be seen together

### 3. Diagnostic slides (answer-list → inline auto-animate morph)
- **Before**: 6 items on one slide, separate answer-list below with coordinator labels
- **After**: 4 slides — 2 auto-animate pairs (3 items each). Period `.` morphs into `, and` / `, but` / `, so` with blue underline inline
- **Principle violated**: The correction should BE the sentence, not alongside it

### 4. Color/contrast overhaul
- Answer green: `#1e7e34` → `#0d5e1a`
- Pedagogical teal: `#1a6b5a` → `#0d4a3d`
- **Principle violated**: Projection contrast — colors that look fine on a monitor wash out under projection

### 5. Font size minimums enforced
- Lead-in: 0.7em/0.75em → 0.9em/1.2em
- All answer slides: 0.85em → 0.95em (headings), 0.75em → 0.9em (Why text)
- Hard rule: never below 0.85em for any text a student must read
- **Principle violated**: Readability at distance — what works on a laptop fails on a projector

### 6. Formula slides (annotated clutter → clean auto-animate)
- **Before**: S V annotation rows with `&nbsp;` spacing, transparent borders on elements that never change
- **After**: Entry shows both versions with transparent borders only on CHANGED elements. Reveal dims simple sentence, adds blue underlines + box-shadow on new S+V. No annotation rows.
- **Principle violated**: Coherence — extraneous material distracts from the key change

### 7. Strategy slide (crammed → split with example pair)
- **Before**: 3 strategy steps + worked example on one slide
- **After**: Strategy steps on one slide. Worked example in separate auto-animate pair (entry: sentence, reveal: S+V underlines)
- **Principle violated**: Segmenting — complex material must be broken into learner-paced chunks

### 8. Answer slides — complete format overhaul
- **Before**: Classification visible on entry, formula as fragment, generic "One S-V pair" explanation, 0.7em text, broken flex layout with centered "..." spacer
- **After**: Classification + formula + sentence with S/V annotations all revealed on click (matching fragment-index per item). S words underlined blue with italic `(S)` label. V words underlined orange with italic `(V)` label. Real sentences from textbook text. Max 3 per slide. Font 0.95em. Coordinator words highlighted in white.
- **Principle violated**: Why column must show the answer IN CONTEXT, not as abstract explanation

### 9. Coordinator slides (static compound → auto-animate two sentences)
- **Before**: Static compound sentence on each coordinator slide
- **After**: Auto-animate pair — entry shows two simple sentences, reveal morphs period to `, and`/`, but`/`, or`/`, so` with blue underline
- **Principle violated**: Auto-animate is for transformation, not decoration

### 10. Demo slide (one crammed slide → 3 auto-animate steps)
- **Before**: All 3 steps on one pedagogical slide at 0.7em
- **After**: 3 auto-animate slides (one per step), 0.85em, each step dims previous
- **Principle violated**: Segmenting + one step per slide

## What I learned

### The root cause: I was pattern-matching HTML, not designing for learning
Every mistake traces back to the same error — I copied patterns from existing code without asking: *"What does the learner need to see and understand at this moment?"*

### The specific failures:
1. **I optimized for structure, not comprehension** — built slides that "followed the rules" but didn't serve the learner
2. **I used template font sizes without questioning them** — 0.7em in the template became 0.7em everywhere
3. **I treated auto-animate as a visual effect** — not as a pedagogical tool for showing transformation
4. **I crammed information to reduce slide count** — violating the "one concept per slide" rule
5. **I wrote abstractions instead of real sentences** — "One S-V pair" instead of "The summers were hot"
6. **I didn't test projection contrast** — colors that work on a monitor fail on a projector

### What sticks after this session:
- The learner's question is the only question that matters
- Projection reality: 0.85em minimum, dark colors for contrast, white/yellow text only
- Auto-animate = structural transformation. Not decoration.
- Max 3 per answer slide. Not a suggestion — a hard limit.
- Real sentences, not abstractions. The Why column must be contextual.

## How to prevent this in future slideshows

### What we already have (made during this session):
- `templates/base-slides-template.html` rebuilt with uncommented, working reference slides
- AGENTS.md updated with mandatory pre-write checklist (10 rules)
- All color references updated in docs (#0d5e1a and #0d4a3d)

### What we still need — the agent execution gap

The checklist and template exist, but I've proven I don't follow them. The problem is an **execution discipline gap** — I skip verification when building slides rapidly.

#### Proposal: Pre-generation ritual (must complete before writing ANY slide)

Before writing a slideshow's HTML, the agent must:
1. **Open and scan the reference template** — confirm the exact pattern for each needed slide type
2. **Verify the color values** — `#0d5e1a` for answers, `#0d4a3d` for pedagogical
3. **Verify the font size minimums** — every text element ≥0.9em labels or ≥1em body
4. **Plan the slide count** — estimate slides needed and confirm no slide has >3 answer items

#### Proposal: Post-generation validation ritual

After writing the slideshow HTML, before declaring it done:
1. Run `npx revealjs-validator` on the output directory
2. Open the file in a browser and visually inspect every slide type
3. Check: are all fragments on answer slides only? Are objectives static?
4. Check: are all auto-animate pairs correctly structured? (matching data-auto-animate-id, data-id on elements)

#### Proposal: Reference slideshow

Create `templates/reference-slideshow.html` — a standalone, complete, functioning slideshow (with real content) that demonstrates every slide type done correctly. This is MORE useful than commented snippets because:
- It's a complete HTML file that opens and works in a browser
- Every slide follows all the rules
- The agent can copy-paste entire sections
- It forces the agent to LOOK at working examples before writing

This reference would contain ~15 slides covering: title, objective, transition, lead-in error pair, diagnostic pair, pedagogical key rule pair, coordinator demo pair, strategy, task with timer, pedagogical demo, answer with S/V annotations, summary, end.

### The meta-lesson

The template, checklist, and skills exist to be USED, not just to exist. My failure pattern is: write slides → check rules later → find violations → fix. The fix is: check rules first → then write.

This requires shifting from "what HTML should I write?" to "what does the learner need to see?" — every single time.
